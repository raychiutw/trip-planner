## 1. Color

來源：<https://developer.apple.com/design/human-interface-guidelines/color>（2026-10-26）

規範重點（原文要旨）：

1. **同色不表示不同意義**：「Avoid using the same color to mean different things.」例：品牌色用來表示 borderless button 可互動，就不要用同色／近似色做不可互動文字。
2. **每個自訂色都要有 light、dark、increased contrast 三種變體**：「If you define a custom color, make sure to supply light and dark variants, and an increased contrast option for each variant that provides a significantly higher amount of visual differentiation.」「Even if your app ships in a single appearance mode, provide both light and dark colors to support Liquid Glass adaptivity.」
3. **不要硬編碼系統色值**：文件列的色值僅供設計參考，實際值每版可能變動。
4. **不要重定義語意色用途**：例如不要拿 separator 色當文字色、secondaryLabel 當背景。
5. **不能只靠顏色傳達資訊**：用文字標籤或圖形形狀補充狀態（色盲）。
6. **Liquid Glass 上的顏色**：玻璃預設無色、取自後方內容。要強調主要動作時「**把顏色套在背景，不是符號或文字**」；「Refrain from adding color to the background of multiple controls.」內容層若已很多彩，toolbar / tab bar 走單色或選差異足夠的 accent。內容層與控制項的相似色不要重疊，**捲動靜止態（頁頂）也要清楚可讀**。
7. **iOS 背景階層**：system 組（systemBackground / secondary / tertiary）與 grouped 組；Primary = 整體 view，Secondary = view 內的分組，Tertiary = secondary 元素內的分組。前景色：label / secondaryLabel / tertiaryLabel / quaternaryLabel / placeholderText / separator / opaqueSeparator / link。
8. **macOS**：有完整動態系統色清單（labelColor、controlAccentColor、selectedContentBackgroundColor、separatorColor、keyboardFocusIndicatorColor、alternatingContentBackgroundColors 等）；App accent color 只在系統 accent 設為 multicolor 時生效，使用者改了就覆蓋（固定色的 sidebar icon 例外）。

數值：頁面只有「對比與可讀性」的定性規定；**Color 頁本身沒有對比比值**（比值在 Dark Mode 與 Accessibility 頁，見 §2、§7）。system color 的 light/dark/increased-contrast 實際色值為圖片表格，未取得。

【Web 註記】`prefers-color-scheme`、`prefers-contrast: more`、`forced-colors` 是 Web 對應；Apple 要求的「三變體」在 Web 即 light / dark / `prefers-contrast: more` 各一組 token。

## 2. Dark Mode

來源：<https://developer.apple.com/design/human-interface-guidelines/dark-mode>（2026-10-26）

1. **避免 app 內自訂外觀開關**：「Avoid offering an app-specific appearance setting. … people have to adjust more than one setting … they may think your app is broken because it doesn’t respond to their systemwide appearance choice.」
2. **兩種外觀都要好看**，且 Auto 會在 app 執行中切換。
3. **對比下限**：「At a minimum, make sure the contrast ratio between colors is no lower than **4.5:1**. For custom foreground and background colors, strive for a contrast ratio of **7:1**, especially in small text.」
4. **要在 Dark Mode × Increase Contrast × Reduce Transparency（各別與同時）測試**：Dark Mode 開 Increase Contrast 可能讓深字對深底**反而**對比降低。
5. **Dark 色不是 light 的單純反相**：背景較暗、前景較亮。
6. **iOS/iPadOS 背景分 base 與 elevated 兩組**：「The base colors are dimmer, making background interfaces appear to recede, and the elevated colors are brighter, making foreground interfaces appear to advance.」popover、modal sheet、多工視窗等前景介面自動由 base 轉 elevated；「Using a custom background color can make it harder for people to perceive these system-provided visual distinctions.」
7. **白底圖片要柔化**：含白底的內容圖在深色環境略微調暗，避免「發光」。
8. **圖示**：深淺兩外觀各要看得清楚；必要時分兩套（例：邊緣在深底消失的圖示加細框）。
9. **macOS desktop tinting**（graphite accent）：自訂元件若有可見底且處於中性狀態，可帶一點透明讓視窗背景色透入；有顏色的狀態不要加透明。

【Web 註記】第 1 點與本專案 `ThemeToggle` 有衝突（見 §13）。base/elevated 在 Web 即「底層頁面 < sheet/popover/第三欄」的亮度階梯；實際色碼未取得，不能拿 Apple 色碼當驗收值。

## 3. Typography

來源：<https://developer.apple.com/design/human-interface-guidelines/typography>（2026-10-26）

**預設與最小字級（原生 pt）**

| 平台 | 預設 | 最小 |
|---|---|---|
| iOS, iPadOS | 17 pt | 11 pt |
| macOS | 13 pt | 10 pt |

（同表另列 tvOS 29/23、visionOS 17/12、watchOS 16/12，與本專案無關。Accessibility 頁有相同表。）

**重點規範**

- 「In general, avoid light font weights」：偏好 Regular / Medium / Semibold / Bold，避開 Ultralight / Thin / Light；自訂字體若偏細，字級要**大於**建議值。
- 自訂字體須實作 System font 自帶的行為（Dynamic Type、Bold Text）。
- 「Minimize the number of typefaces you use」；階層用 weight、size、color 調整，且文字被放大時**維持相對階層**。
- **放大時不是全部等比放大**：使用者放大字級是要看內容，例如 tab 標題不需要跟著放大。
- Dynamic Type 規範：版面要能容納所有字級；放大時 truncation 盡量少，「aim to display as much useful text at the largest accessibility font size as you do at the largest standard font size」；橫向並排元素放大時改**堆疊**；多欄文字放大時減少欄數；重要元素維持在上方。
- 行高：多行文字可用 loose leading；列高受限時可 tight leading，但「If you need to display three or more lines of text, avoid tight leading even in areas where height is limited.」
- **macOS 不支援 Dynamic Type**。

**iOS 預設字階（Large / default，size / leading，pt）**：Large Title 34/41、Title 1 28/34、Title 2 22/28、Title 3 20/25、Headline 17/22（Semibold）、Body 17/22、Callout 16/21、Subhead 15/20、Footnote 13/18、Caption 1 12/16、Caption 2 11/13。xSmall 到 xxxLarge 與 AX 級另有各自表（原文有，本篇不全抄）。

**macOS 字階（size / line height，pt）**：Large Title 26/32、Title 1 22/26、Title 2 17/22、Title 3 15/20、Headline 13/16（Bold）、Body 13/16、Callout 12/15、Subheadline 11/14、Footnote 10/13、Caption 1 10/13、Caption 2 10/13（Medium）。

【Web 註記】
- Apple 行高（Body 17/22 ≈ 1.29）是原生 UI 值；本專案 body 16/26（≈1.63，中文內文）是 owner 的版面決定，**不是違規**。可驗的是「無細字重」「放大 200% 不裁切」「不靠字級放大破版」。
- 本專案 `eyebrow` 10px、`bottom-nav-label` 11px 低於 iOS 最小 11 pt，比較口徑見 §13。pt≠px，11pt 約對應 11 CSS px 僅為粗估，非規範。

## 4. Layout、Safe area、Spacing

來源：<https://developer.apple.com/design/human-interface-guidelines/layout>、<https://developer.apple.com/design/human-interface-guidelines/accessibility>（2026-10-26）

**Layout 頁**

- 視覺階層：重要內容放上方與 leading 側；對齊與縮排表達階層；用留白／容器／分隔線分組；progressive disclosure 讓版面乾淨。
- **區分控制與內容**：「Instead of applying a solid or semi-opaque background color beneath controls, use a scroll edge effect to visually elevate controls above content.」全螢幕背景內容應**延伸到 sidebar / toolbar / tab bar 之下**。【原生】scroll edge effect 為 API；Web 可類比為漸層遮罩，非必要。
- **適應性**：依「size class」而非 device 或 orientation 決定版面；「Keep functionality the same as size classes change」，但可改變同時顯示多少功能（例如空間大時 tab bar 換成 sidebar）。
- **Safe area**：「Respecting the safe area is essential to make sure system UI and hardware features … don’t obstruct content and controls.」
- macOS：「Avoid placing controls or critical information at the bottom of a window」（使用者常把視窗底緣移出螢幕）。
- 要在多裝置、多 size class、多語系、多字級下預覽。

**Spacing / 目標尺寸（Accessibility 頁，Mobility）**

| 平台 | 預設 control 尺寸 | 最小 |
|---|---|---|
| iOS, iPadOS | 44×44 pt | 28×28 pt |
| macOS | 28×28 pt | 20×20 pt |

- 「Consider spacing between controls as important as size.」有 bezel 的元素周圍約 **12 pt** padding；無 bezel 的元素約 **24 pt**。
- Buttons 頁：「a button needs a hit region of at least **44x44 pt**」。

**未在這兩頁找到**：頁面邊距（margins）的具體 pt 值、8pt 格線等數值——Layout 頁此版沒有列（只有 tvOS 的 60/80 pt safe area 與 grid 表，與本專案無關）。不補。

【Web 註記】
- safe area 的 Web 對應是 `env(safe-area-inset-*)` 與 `viewport-fit=cover`。【可驗】底部玻璃膠囊、sheet 底部按鈕列在 iPhone 瀏覽器／PWA standalone 不被 home indicator 遮。
- 44 pt 在專案為「44 CSS px 目標」（owner 決定）；WCAG 2.5.8 Web AA 為 24 CSS px。三者分開（見 DESIGN.md「Web 設計驗收與來源」）。

## 5. Materials（Liquid Glass / vibrancy / 透明度）

來源：<https://developer.apple.com/design/human-interface-guidelines/materials>（2026-10-26）

- Liquid Glass 是**控制與導覽層**（tab bar、sidebar、toolbar）浮在內容層之上的材質。「**Don’t use Liquid Glass in the content layer.**」內容層用 standard materials；唯一例外是內容層裡的暫態互動控制（slider、toggle 啟動時）。
- 「Use Liquid Glass effects sparingly.」只留給最重要的功能性元素。
- 兩種 variant：**regular**（模糊並調整亮度，文字多的元件如 alert、sidebar、popover 用）與 **clear**（高度透明，僅限在豐富媒體背景上）。clear 玻璃下方內容很亮時，加 **35% 不透明度**的暗色 dimming layer。
- 變體外觀會隨系統設定（使用者選的玻璃樣式、**降低透明度**、**提高對比**）改變——頁面只這樣一句帶過，**沒有更詳細的 Reduce Transparency 專章**（Dark Mode 頁另要求同時測 Increase Contrast + Reduce Transparency）。
- Standard materials：iOS 四級 ultraThin / thin / regular（預設）/ thick。厚的較不透明，對比較好；薄的保留背景脈絡。「Avoid selecting a material … based on the apparent color it imparts」要依語意用途選。
- vibrancy：在材質上用系統 vibrant 色；quaternary label 別放在 thin / ultraThin 上（對比太低）。

【Web 註記】`backdrop-filter` + 半透明底是近似；Apple 的 Reduce Transparency 在 Web 對應 `prefers-reduced-transparency: reduce`（支援度有限，需有降級策略）與 `prefers-contrast: more`。本專案 `css/tokens.css` 已有兩者區塊（#1422 為其失效問題，見 10-09 篇）。【可驗】開啟降級後玻璃面變實心、文字對比不降。

## 6. Navigation

### 6.1 Tab bars

來源：<https://developer.apple.com/design/human-interface-guidelines/tab-bars>（2026-10-26）

- 用 tab bar **導覽**，不放動作（動作放 toolbar）。
- **導覽狀態保留**：切換 tab 不丟各 section 的導覽位置。
- 切到不同區塊時 tab bar 要**維持可見**（modal 蓋住除外）。
- **不要 disable 或隱藏** tab 按鈕，內容為空就說明原因。
- 「Avoid overflow tabs」；tab 數量宜少。（頁面無「5 個」硬上限，只說 iPadOS 自訂時預設宜 **5 個以內**。）
- **要有 tab label**，盡量單字；圖示偏好 filled 版本；badge 只給關鍵資訊。
- 避免 tab 標籤色與內容層背景色相近；內容豐富時用單色或差異足夠的 accent。
- iOS：tab bar **浮在內容底部，Liquid Glass 背景**，內容可從下方透出；可有專用搜尋 tab；可在捲動時縮小（minimize）。
- iPadOS：tab bar 在頂部，可轉換為 sidebar。

### 6.2 Sidebars

來源：<https://developer.apple.com/design/human-interface-guidelines/sidebars>（2026-10-26，頁面 change log 2026-06-08）

- Sidebar 需大量空間；空間有限時 tab bar 更合適。
- sidebar 可浮在 Liquid Glass 層，內容可延伸到其下。
- **階層不超過兩層**；兩層時群組標題要簡短。
- 「Avoid hiding the sidebar by default to ensure that it remains discoverable.」可提供顯示／隱藏；macOS 可隨視窗縮小自動收合。
- sidebar icon 預設跟 app accent；macOS 使用者改系統 accent 時預期 icon 跟著變，固定色須「serve a clear purpose」並少用。
- macOS：「Avoid putting critical information or actions at the bottom of a sidebar.」
- 大空間用 sidebar、小空間用 tab bar 是 Apple 的建議適應策略。

### 6.3 Toolbars / Navigation bars

來源：<https://developer.apple.com/design/human-interface-guidelines/toolbars>（2026-10-26，change log 2025-12-16）

- toolbar 含：標題、導覽控制（返回、搜尋）、動作。iOS 的 navigation bar 就是導覽用 toolbar。
- **標題**：「Don’t title windows with your app name」；簡潔，**少於 15 字元**留空間給其他控制項。
- **返回與關閉用標準符號，不用「Back」「Close」文字標籤**：「Prefer the standard symbols for each, and don’t use a text label that says Back or Close.」
- 動作偏好**無邊框的系統符號**；主要動作用 prominent 樣式，「Only specify one primary action, and put it on the trailing side」。
- 「Reduce the use of toolbar backgrounds and tinted controls.」避免自訂背景干擾系統背景效果。
- 群組**最多三組**；文字標籤的鈕之間要插入固定間距，免得字連在一起。
- 與內容色相近的標籤色要避免；內容多彩時 toolbar 用單色。
- iOS：large title 捲動時轉標準標題。
- macOS：每個 toolbar 項目也要有 menu bar 指令；toolbar 項目沒有 bezel。

### 6.4 Sheets 與 Modality

來源：<https://developer.apple.com/design/human-interface-guidelines/sheets>（change log 2026-03-24）、<https://developer.apple.com/design/human-interface-guidelines/modality>（2026-10-26）

- sheet 用在**要資訊或簡單任務**；複雜、冗長流程改全螢幕或獨立視窗。
- **一次只一個 sheet**：要開第二個就先關第一個。
- 按鈕語意：Cancel/Close（不存直接關）、Done（完成並關）、Back（多步驟上一步，不是用來關閉）。**Done 一定要搭配 Cancel 或 Back**；「Avoid showing all three buttons」。
- iOS/iPadOS 單頁 sheet：**Cancel 在頂部 toolbar 的 leading，Done 在 trailing**（2026-03-24 更新過按鈕位置）。
- 可調整高度的 sheet：**medium**（約半高）與 **large**；要有 **grabber**（可點擊循環 detent，也供 VoiceOver 使用）。
- 「Support swiping to dismiss a sheet」；有未存變更時滑動關閉要用 action sheet 確認。
- iPadOS 偏好 page / form sheet 樣式（置中、背景變暗）。
- macOS sheet 是浮在父視窗上的圓角卡片，父視窗變暗。
- Modality：只在有明確益處時用；任務要簡單短小；避免「app 中的 app」（modal 內層層下鑽）；**一定要有明顯的關閉方式**；可能遺失資料時關閉前要確認；要有標題說明任務；一次只看到一個 modal（alert 除外，且 alert 也只能一個）。

【Web 註記】Account sheet、操作頁堆疊面板直接對應這節。「sheet 內再下鑽」與「Done 單獨存在」是可驗的檢查點。

## 7. Accessibility

來源：<https://developer.apple.com/design/human-interface-guidelines/accessibility>、<https://developer.apple.com/design/human-interface-guidelines/motion>（2026-10-26）

- **放大字級至少 200%**：「Ideally, give people the option to enlarge text by at least 200 percent」（watchOS 140%）。
- **對比（引用 WCAG AA，Accessibility Inspector 所用）**：

| 文字大小 | 粗細 | 最小對比 |
|---|---|---|
| 到 17 pt | 全部 | 4.5:1 |
| 18 pt | 全部 | 3:1 |
| 全部 | Bold | 3:1 |

  「If your app doesn’t provide this minimum contrast by default, ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on.」且要在淺色與深色兩種外觀都檢查。【Web 註記】此表是**原生**指引；Web 驗收以 WCAG 1.4.3 的 large-scale 定義為準（專案既有規則：bold 不自動 3:1）。
- 優先用系統色（自帶加強對比變體）。
- **不靠單一顏色**：形狀／圖示補充。
- **Reduce Motion**：「reducing automatic and repetitive animations, including zooming, scaling, and peripheral motion」。做法：收緊彈簧減少回彈、動畫跟隨手勢、避免 z 軸深度動畫、**x/y/z 軸轉場換成淡入淡出**、避免進出模糊的動畫。
- 少用**計時自動消失**的 UI（輔助科技使用者需要更多時間），偏好明確動作關閉。
- **手勢要有替代**：滑動關閉要另有按鈕。避免複雜多指手勢。
- 鍵盤：支援純鍵盤操作（Full Keyboard Access），不覆寫系統快捷鍵。
- Motion 頁：動畫要有目的；「Make motion optional」；常用互動少加動畫；「Let people cancel motion」不要讓人等動畫結束。
- Assistive Access：難復原的動作「ask for confirmation twice」。【原生】

## 8. Lists 與 Tables

來源：<https://developer.apple.com/design/human-interface-guidelines/lists-and-tables>（2026-10-26）

- 以**文字**為主時用 list/table；圖片多或尺寸差異大改 collection。
- 選取回饋：導覽階層的列表**持續高亮**目前選取列；選項型列表**短暫高亮後出現勾選**。
- 文字簡短，減少截斷；窄時中間省略（保留頭尾）可讀性較好；多欄表用描述性欄標。
- 樣式：iOS grouped 以標頭、頁尾與間距分組；macOS bordered 用交替列底色。
- macOS：欄標頭點擊排序（再點反向）、可調欄寬、階層資料用 outline view。
- 本頁**無列高、分隔線的數值**；不補。

## 9. Buttons

來源：<https://developer.apple.com/design/human-interface-guidelines/buttons>（2026-10-26，change log 2025-12-16）

- **hit region 至少 44×44 pt**；周圍留足空間以便視覺區分。
- **自訂按鈕一定要有 press state**，否則像沒反應。
- 最可能的動作用 **prominent 樣式，且每個 view 只放一到兩個**；多個選項要區分主次時用**樣式不是尺寸**（同組按鈕同尺寸）。
- Role：Normal / Primary / Cancel / Destructive。「Don’t assign the primary role to a button that performs a destructive action, even if that action is the most likely choice.」
- 按鈕標籤色避免與內容層背景相近。
- 內容：圖示用熟悉的符號；用文字時以動詞開頭（Add to Cart）；macOS 開啟其他視窗／視圖的按鈕標題加 `…`。
- 長時間動作：按鈕內顯示 activity indicator，標籤可變（Checkout → Checking out…）。
- macOS image button 周圍約 **10 px** padding；square button 與 help button 放在 view 內，不放視窗框（toolbar）。

## 10. Menus 與 Pop-up buttons

來源：<https://developer.apple.com/design/human-interface-guidelines/menus>（change log 2026-06-08）、<https://developer.apple.com/design/human-interface-guidelines/pop-up-buttons>（2026-10-26）

- 標籤用動詞或動詞片語、title-style 大寫、去掉冠詞；**不可用項目顯示為變暗**但選單本身仍可開啟。
- 需要更多輸入才能完成的動作，標籤後加 `…`。
- **圖示少用且有目的；同組要嘛全有、要嘛全無**（2026-06-08 更新過）。
- 重要／常用項目排前；相關指令分組以分隔線隔開；選單別太長，可用 submenu 縮短，但 submenu **只用一層**、約 **5 項**以上就考慮另開選單；用 submenu 不用縮排。
- 開關型項目：標籤隨狀態變（Show Map / Hide Map）或用勾選。
- Pop-up button：用於**互斥選項的平面清單**；要多選、動作、submenu 就改用 pull-down button；提供有用的預設值；用前導標籤讓人不開啟也能預測選項。

## 11. Search fields

來源：<https://developer.apple.com/design/human-interface-guidelines/search-fields>（change log 2026-06-08）（2026-10-26）

- 欄位含搜尋圖示、清除按鈕、placeholder；placeholder 說明可搜什麼。
- **輸入即搜尋**；可顯示最近搜尋或預測建議；結果最相關在前，可用 scope bar 縮小範圍（預設較廣）。
- iOS 搜尋位置三選一：作為 tab、在 toolbar（底部有空間優先）、或 inline 於內容旁。
- iPadOS / macOS：**toolbar 尾端**放搜尋欄；要篩選 sidebar 時放 sidebar 頂部；要探索型頁面時放進 sidebar / tab bar 作專屬區域。
- 專屬搜尋區進入時宜立即聚焦（iPad 只有虛擬鍵盤時例外，避免鍵盤擋住畫面）。
